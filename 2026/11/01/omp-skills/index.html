这 15 个 skill 都不是我写的，是我一个个挑出来装进 omp 的。它们平时躺在 ~/.omp/agent/skills/ 里，什么时候被叫起来，看我那天在干什么。

skill 是怎么起作用的

一个 skill 就是一个文件夹，入口是一份 SKILL.md。开头写着名字和一段 description，正文是给模型看的规则，复杂的再挂一层 references/，用到才读。

模型每次只看到名字和那一行 description，判断这活儿归谁管，再整篇读进来干活。所以装 skill 的思路不是给它加功能，是把“遇到这类事情该怎么办”写成文件放在手边，省掉每次重新交代。

开工之前：先把方案问清楚

想法还很粗的时候，我一般先叫 think。它会把问题往回问：这事值不值得做，先后顺序怎么排，做到什么程度算完。方案没定下来之前它不写代码，也不搭脚手架。

碰到完全不熟的领域，用 learn，从找材料、读懂、列提纲、填内容一路走到成稿，六个阶段走一遍，最后自己再复核。两个 skill 都适合“我心里只有一个大概”的时候。

做界面：从方向到选型

真要动手做页面，先叫 ui，它出组件和排版，要求是得有明确方向，默认提示词能生成的那种长相它自己就不认。判断标准来自 emil-design-eng，这组的总纲，讲那些说不清但一眼能看出差别的细节，也是我装的里面最长的一份。

界面做出来像 AI 拉的，用 unslop 收拾，紫色渐变、光晕、emoji 标签、New ✨ 徽章、间距不匀，它按顺序一项项过。方向拿不准的时候用 prototype，同一块界面出几版，摆在选择器里翻着看，挑中哪个留哪个。需要选库就交给 pick-ui-library，数字输入、OTP、图表、命令菜单、虚拟化、拖拽、toast 都有指定答案，省得让模型自己手搓一个再装个没人维护的包。

界面做完，专门找它坏在哪

break-ui 是拿来撞的：超长名字、不能断行的邮箱、零条数据、超大计数、非拉丁文字全塞进去，撞坏的地方连同修法一起列出来。

mobile-native 只修“电脑上能用、手机上不对劲”那类毛病，点击高亮闪一下、100vh 在地址栏收起后错位、输入框获得焦点把页面放大、内容钻到刘海底下。还有一个只盯 toast 的 ask-sonner，弹不出来、弹两遍、样式丢了、被弹窗盖住、不跟随深色模式，它都能查。

桌面 App 就是另一件事了，native-feel-cross-platform-desktop 管 macOS 和 Windows 同时保持原生手感这类架构选择，内容来自 Raycast 2.0 的技术复盘，八条原则、四层架构、75 项上线检查。

写东西的时候

中文英文的稿子都归 write，改稿、去 AI 味、发布说明、公开回复、多语言文案，标点也管，交稿前会跑一遍检查脚本。这篇也是按它的规则写的。

Swift 和文档

写 SwiftUI 的时候有 swiftui-pro 做代码审查，看 API 用法、性能、无障碍、废弃接口。write-swift 讲现代 Swift 怎么写，值类型、Swift 6 并发、泛型、Swift Testing。要出 PDF 就换 kami，简历、一页纸、白皮书、PPT 都是它排的。
